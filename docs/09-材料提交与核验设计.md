# 09 材料提交与核验设计

> 状态：**已实现**（后端 + 前端材料区）。
> 材料提交发生在**受理之前**：先由条件判定算出要什么材料，逐项交齐并通过核验，才允许并联提交。

## 1. 为什么材料必须先于受理

材料清单不是静态的——它由**条件判定**产出（例如"面积 ≥ 300㎡ 才需要消防材料"、
"经营热食才需要油烟净化设施证明"）。而条件判定又依赖用户填写的申请信息。

所以不可能"提交申请"和"上传材料"在同一次请求里完成，流程必然拆成三段：

```
① 填写申请信息                        POST /api/materials/intake
     信息采集 -> 条件判定 -> 材料清单       → 受理号 intake_id + 结构化材料清单
② 逐项提交材料                        POST /api/materials/{intake_id}/{material_id}/files
     拍照 / 相册 / 选文件 -> 即时核验       → 该项状态：待提交 / 已通过 / 需补正
③ 材料齐备后开始办理                   POST /apply（带 intake_id）
     材料核验 -> 并联提交 -> 各部门办结 -> 进度
```

不传 `intake_id` 时 `/apply` 保持原有行为（一次跑完全程），供 CLI 演示与老调用方使用。

## 2. 材料条目模型

材料在场景配置（`scenarios/*.json`）的 `materials` 字典里定义，条件规则用 **id** 引用：

```json
"materials": {
  "id_card": {
    "name": "法定代表人身份证",
    "reason": "用于确认申请人身份",
    "form": "正面、反面各一张，四角完整、文字清晰",
    "accept": ["jpg", "jpeg", "png"],
    "slots": ["正面", "反面"],
    "required": true
  }
}
```

| 字段 | 说明 |
| --- | --- |
| `id` | 稳定标识，`base_materials` / `add_materials` 都用它，**存进办理单的也是它** |
| `name` | 中文名（只给用户看） |
| `reason` | **为什么要交**——群众最关心，必须给 |
| `form` | 怎么给（形式要求） |
| `accept` | 接受的扩展名 |
| `slots` | 具名槽位，见第 3 节 |
| `multiple` / `max_files` | 多页材料模式（`slots` 为空时才生效） |
| `required` | 是否必交 |

展示层一律走 `name`，界面与对话里不出现 id（见 `docs/08` 文案规范）。

## 3. 槽位：张数上限怎么定

一份材料有两种形态，由 `slots` 是否为空决定：

**具名槽位**（`slots: ["正面", "反面"]`）——每个槽位**恰好一张**，槽位数就是张数上限。

- 身份证就是典型：**总共只有正反两面，就规定上传一张正面、一张反面，多余的不收**；
- 缺一个槽位不算齐（状态停在「待提交」）；
- 同一个槽位重复上传会被拒（要换请先撤回原来那张）；
- 超过槽位数量的上传直接被拒，并给出自然语言原因。

**多页材料**（`slots: []` + `multiple: true` + `max_files`）——不固定页数，1 ~ `max_files` 张。
适用于多页合同、多页公司章程这类"页数本来就不固定"的材料。

判定逻辑集中在 `app/materials/spec.py`，是纯函数，便于单测：

| 函数 | 作用 |
| --- | --- |
| `material_specs(scenario, ids)` | 取条目并补齐默认值（槽位数量即张数上限） |
| `reject_reason(spec, files, slot)` | 能否再收一张；不能则返回对用户可见的原因 |
| `missing_slots(spec, files)` | 还缺哪些槽位 |
| `status_of(spec, files)` | 该项状态：待提交 / 已通过 / 需补正 |
| `summary(specs, files_map)` | 整体进度：已通过几项、能否受理 |

## 4. 上传通道：文件从哪来

文件来源**全部由 uni-app 统一 API 提供**，一份代码覆盖两端：

| 用户动作 | uni-app API | H5（调试端） | App（成品端） |
| --- | --- | --- | --- |
| 拍照 | `uni.chooseImage({ sourceType: ['camera'] })` | 手机浏览器可调摄像头；桌面浏览器退化为选文件 | 原生相机 |
| 从相册选 | `uni.chooseImage({ sourceType: ['album'] })` | 选文件 | 系统相册 |
| 选文件（PDF 等） | `uni.chooseFile({ extension })` | 系统文件选择框 | 文件管理 |

传输用 **`uni.uploadFile`（`multipart/form-data`）**，而不是把文件读成 base64 塞进 JSON：

- 跨端统一（H5 走 FormData、App 走原生上传器），能拿到上传进度；
- 能直接读到 HTTP 状态码，便于区分"格式不对 / 太大 / 核验没过"；
- 避免 base64 带来的体积膨胀（约 +33%）与内存占用。

后端用 FastAPI 的 `UploadFile` 接收，因此依赖里多了 `python-multipart`。

## 6. 两级核验与状态机

**形式校验**（`form_check`，纯规则、本地瞬时完成）：扩展名是否被接受、文件是否为空、
体积是否超限（单张 ≤ 10MB）。不通过的直接拒收（HTTP 400），文件不入库。

**内容核验**（核验器，可插拔）：这份材料的照片**是不是真是那份材料**、清不清晰。
按"当前有没有可用的多模态模型"自动选实现：

| 核验器 | 何时启用 | 做什么 |
| --- | --- | --- |
| `VisionChecker` | 配了多模态模型（`TASK_MODEL["verify"] → vision`，即 `qwen-vl`） | 把图片编码成 `data:` URL，连同"这是哪份材料的哪个槽位、用途是什么"一起交给视觉模型，要求它只回 `{"ok": bool, "reason": "一句话原因"}` |
| `StubChecker` | 没配模型 | 一条**可解释**的规则代替模型：图片体积过小判为"不是原图"。零依赖、离线可跑，保留「需补正」闭环 |

**降级策略（关键）**：模型不可用 / 超时 / 返回无法解析 → **一律回落桩规则**。
材料核验是办事链路的必经环节，不能因为模型故障就让群众交不上材料。

不送模型的三种情况：**不是图片**（PDF 没有视觉信息）、**图片过大**（> 2MB，base64 后
请求体还要再涨约 1/3，得不偿失）、**模型不可用**。

判定语义（这条边界容易写错）：

| 结果 | 含义 | 触发 |
| --- | --- | --- |
| `通过` | 收下，该槽位占位 | 形式校验通过 + 内容核验判合规 |
| `需补正` | 收下但标记需补正，**可原地重传** | 内容核验判"不是这份材料 / 看不清" |
| `不通过` | 文件根本收不下，前端要重选 | 格式 / 空文件 / 体积超限 |

> 模型说"这不是身份证"属于**内容问题**，落到 `需补正`（用户重拍重传），而不是 `不通过`
> （那是"文件收不下"的语义）。分错的后果是提示用户"重选文件"而他要的是"重拍"，对不上。

### 提示文案的写法（产品要求，不是文案偏好）

每条"不能收 / 要重传"的说明都要回答三件事，办事人看完能**直接动手**：

1. **是什么问题**——具体到能自证：「这个文件 14.1MB」「这张图只有 516B」「画面里是一张餐桌」；
2. **为什么不行**——对照的规矩：「超过单张 10MB 上限」「不像身份证正面」；
3. **怎么改**——可执行的动作：「压缩后再传」「平放拍，四角进画面，别开闪光灯」。

"怎么改"的来源按优先级：**模型给的 `fix` > 场景配置的 `fix_hint`（支持 `{slot}` 占位）> 通用兜底**。
场景作者最懂每份材料该怎么拍，所以 `fix_hint` 写在 `scenarios/*.json` 的材料条目里，不用改代码。

**形式校验为什么不走模型**：格式与体积是硬规则，跟内容无关；而且格式不对的文件根本解不出图。
本地把判据说具体就够了（说清实际格式、实际大小、上限），没必要花一次模型调用去说"你的文件太大了"。

模型返回的文本一律过 `clean_text()`：压平换行、限长 120 字、**屏蔽 8 位以上连续数字**
（证件号 / 卡号不该被写进落盘的材料记录），且不暴露模型名。

**前端展示**：需补正说明与上传被拒原因都**整段列在对应材料条目下方**，
不再压在 84×84 的缩略图上（那里放不下）；缩略图只保留"已通过 / 需补正"的红绿边框。

换真实实现时只改 `app/materials/verify.py` 里的核验器，调用方完全不用动。

每项材料的状态机：

```
待提交 --(槽位齐 + 核验通过)--> 已通过
   \--(有文件核验不过)--> 需补正 --(同槽位原地重传)--> 待提交 / 已通过
```

要点：**需补正的那张不占名额**，用户可以在同一槽位直接重传，旧文件被自动清掉，不会越积越多。

## 7. 接口契约

| 接口 | 方法 | 用途 |
| --- | --- | --- |
| `/api/materials/intake` | POST | 按申请信息产出材料清单，返回 `intake_id` 与材料条目 |
| `/api/materials/{intake_id}` | GET | 取材料清单与各项状态 |
| `/api/materials/{intake_id}/{material_id}/files` | POST | 上传一张（`file` + `slot` 两个表单字段） |
| `/api/materials/{intake_id}/{material_id}/files/{file_id}` | DELETE | 撤回一张 |
| `/api/materials/{intake_id}/{material_id}/files/{file_id}` | GET | 读回文件（前端缩略图 / 预览） |

创建清单的响应（材料区的渲染数据源）：

```json
{
  "intake_id": "CL0001",
  "message": "根据您的情况，需要提交 4 份材料，材料没通过前无法受理。\n\n【材料 1/4】…",
  "summary": {"total": 4, "passed": 0, "ready": false},
  "materials": [
    {
      "id": "id_card", "name": "法定代表人身份证",
      "reason": "用于确认申请人身份", "form": "正面、反面各一张…",
      "accept": ["jpg", "jpeg", "png"], "slots": ["正面", "反面"],
      "multiple": false, "max_files": 2,
      "status": "待提交", "missing_slots": ["正面", "反面"],
      "files": [
        {"file_id": "a1b2c3", "slot": "正面", "filename": "正面.jpg", "size": 204800,
         "status": "已通过", "reason": "", "url": "/api/materials/CL0001/id_card/files/a1b2c3"}
      ]
    }
  ]
}
```

**受理前置校验是两道的**：前端"开始办理"按钮置灰，后端 `material_gate()` 再拦一次（HTTP 400），
`MainAgent._resume` 里还有第三道兜底（材料没齐直接报错，不会悄悄受理）。

### 受理入口：两条路径共用一套编排

办理（流程节点打勾、并联提交、各部门办结）**只有一套实现**，由 `MainAgent` 承担；
两个入口都只是它的驱动方式：

| 入口 | 面向 | 过程 |
| --- | --- | --- |
| `POST /apply` | 表单式（当前前端） | 表单一次填完 → `POST /api/materials/intake` → 上传 → `/apply`（带 `intake_id`） |
| `/api/session` + `/api/chat` + `/api/fields` → `/apply` | 对话式（`docs/08` 规划） | 逐字段追问 → 采齐后返回材料清单 → 上传 → `/apply`（带 `intake_id` + `session_id`） |

约定：

- **服务层不再自己受理**。`AgentService` 只负责会话状态机（意图路由、逐字段采集、
  材料清单产出、进度查询），绝不再自己 `gov.submit`——否则会产出一张缺流程节点、
  缺核验记录、并联事项永远停在"已受理"的办理单。
- 对话式路径字段采齐后返回 `intake_id` 与 `material_view`（见 `TurnResponse`），
  前端据此渲染材料区；随后调 `/apply` 时带上 `session_id`，后端在编排结束后
  用 `AgentService.attach_case()` 把办理单挂回会话，会话内的"进度到哪了"依旧可用。
- `material_view` 给界面用（中文名 / 槽位 / 状态 / 文件）；`materials` 字段仍是
  结构化 id 列表（与 `items` 一致），**不要在界面上直接展示 id**。

### 实时预判：正式清单之前先给预估

用户还在填表 / 对话的过程中，就把"大概要办什么、要交什么"提前告诉他，
而不是等采齐后一次性弹出。

接口 `POST /api/preview {scenario_id, answers}` 返回
`{items, item_names, materials, material_names, notes}`；
会话接口（`/api/chat`、`/api/fields`、`/api/sessions/{id}`）的每次返回也带同样的 `preview` 字段。

三条约束：

1. **只读**：不创建材料收集单、不动流程节点、不落库——反复调用不留任何痕迹；
2. **无副作用**：条件判定是纯函数（`app/agents/condition_agent.py::evaluate_conditions`），
   可任意频率重算；前端做了 500ms 防抖（`stores/case.ts::schedulePreview`）；
3. **不是最终结论**：字段采齐后才产出正式清单（`intake_id`）。界面上必须区分两者
   ——改动面积、招牌这类会影响结论的字段时，清单本来就会变，这是**正确**行为，
   但要让用户知道"以最终确认为准"。

> 它**不能**当作流程的首个节点：预判依赖已采集的字段，字段没采时只剩基础清单（等于没判定）。
> 它是挂在"接受输入"这一层的**旁路计算**，不是流程节点。

## 8. 前端交互（对应 `docs/07`）

- 材料区**独立于**「申请信息」表单，位于表单与进度看板之间。
- 每项材料一行：名称 + 为什么 + 怎么给 + 状态徽标 + 槽位格 / 缩略图。
- 具名槽位渲染成一个个格子：已交显示缩略图与大小（可撤回），需补正显示红框与原因（可重传 / 删除），空槽位点击即发起拍照或选文件。
- 多页材料渲染成缩略图流 + "＋"卡片，卡片上标 `已交/上限`。
- 材料区顶部显示"已通过 x/y"与进度条；底部说明是否可开始办理。
- 缺材料时对话区同步播报（`intake` 接口返回的 `message`），逐项说明"要什么 / 为什么 / 怎么给"。

**没有做电子证照共享**（`egov`）：本阶段所有材料都要求用户上传，链路单一、便于验证。
真实政务里"授权共享免提交"是"高效办成一件事"的核心卖点，如后续要做，
在材料条目上加一个 `source` 字段并新增一个授权接口即可，现有上传链路不受影响。

## 9. 与真实政务的衔接

| 能力 | 桩阶段 | 真实阶段 |
| --- | --- | --- |
| 文件存储 | 本地磁盘 `data/runtime/materials/` | 对象存储（OSS / COS）+ 文件编号 |
| 多模态核验 | 已接 MoMA 视觉模型（`qwen-vl`）看图判断是否合规件；模型不可用回落桩规则 | 更细的**要素级**校验（证号 / 有效期 / 与表单字段比对），而不只是"是不是这类件" |
| 电子证照共享 | 未做（全部走上传） | 对接本地电子证照库，加 `source` 字段与授权接口 |
| 材料流转部门 | 不流转 | 按事项把材料附件推送给各部门 |
| 敏感信息保护 | 仅落本地磁盘 | 加密传输、访问控制、脱敏留存 |

## 10. 测试与验算

```bash
python tests/test_materials.py    # 材料链路：清单 / 槽位 / 核验 / 补正 / 撤回 / 持久化 / 受理拦截 / 视觉核验
python tests/test_flow.py         # 原有编排闭环（材料改造后行为不变）
```

`tests/test_materials.py` 覆盖：条件路由产出清单、具名槽位一槽一张且多传不收、
格式与空文件被拒、过小图片判为需补正并可原地重传、多页材料 1 ~ `max_files`、
撤回后状态回落、落盘重载、材料未齐时 `material_gate` 拦截、齐备后从材料核验续跑生成办理单。

视觉核验部分（用 `FakeSession` 喂预设回复，不联网）：模型回复带代码块/解释文字时的解析容错、
多模态消息形状（system + user 的 text/image_url 数组）、模型判不合规 → `需补正` 且转达原因、
非图片与超大图不送模型、**模型异常/乱码/未启用时回落桩规则**、形式校验优先于模型调用，
以及**接线测试**——`MaterialService` 真的把核验器与槽位传下去、`VerifyAgent` 按子 Agent 角色装配核验器。
