# 08 对话交互设计（自然语言办事）

> 本文先回答"现在到底跑到哪一步了"，再给出**对话区**与**回复文案**的设计要求。
> **尚未实现**，落地位置见文末清单。

## 1. 先回答：现在只是演示吗？为什么一按就瞬间完成？

**是的，当前是端到端桩实现（演示），不是真实办理。** 每个环节都还没有真实耗时：

| 环节 | 现状 | 为什么"瞬间完成" |
| --- | --- | --- |
| 咨询 | `MoMAClient.chat()` 桩：原样回显输入 | 不调模型、不发网络请求 |
| 信息采集 | 前端表单一次填完 | 没有多轮追问 |
| 条件判定 | 规则引擎（**真跑**） | 纯本地计算 |
| 材料核验 | `VerifyAgent` 桩：恒返回"通过" | **完全不读材料内容** |
| 部门办理 | `MockGovServices` 内存模拟 | 无网络、无等待 |
| 进度推进 | `ItemAgent` 直接返回"已办结" | 没有真实流转 |

整条链路是**毫秒级**跑完的本地模拟。

真实接入后的时间尺度会发生质变：

- **咨询 / 材料核验**：走 MoMA 模型 → 秒级，且可能失败、需重试
- **部门办理**：对接真实政务系统 → **异步、天级**，进度靠回调或轮询
- **材料**：必须由用户**真实提交**（见 `docs/09`）

> 也就是说：**"按下就完成"是桩实现的产物**，不是设计目标。真实形态下，界面上大量时间处于"等待中/待补正"。

## 2. 对话区（AI 必须能说人话）

### 2.1 现状的问题

1. **没有输入框**：界面左侧的"聊天区"目前只是**事件日志展示**，用户无法提问。
2. **开场白被写死**：`frontend/src/stores/case.ts` 里 `this.utterance = scenario.opening`，
   即"我想在学校旁边开一家牛肉面馆"。用户改了表单它也不变 → **显示内容与事实不符**。
3. **咨询能力形同不存在**：`route_intent(utterance)` 永远拿到同一句话，永远判成 `apply`。
4. **表单与对话脱节**：用户实际填的是表单，而对话里显示的却是场景固定文案。

### 2.2 设计要求

- **对话区必须有输入**：底部输入框 + 发送按钮；消息分「我」与「办事助手」两类气泡。
- **一句话先说完**：用户可以直接说"我想在学校旁边开一家牛肉面馆"，助手从中抽取字段并**回显确认**，缺什么问什么。
- **随时插问**：填表过程中用户问"健康证要多少钱""没有营业场所能办吗"，走**咨询意图**回答，答完**回到原来的采集位置**，不清空已填内容。
- **多轮上下文**：记住已填字段、已答问题、当前办理单号，避免重复询问。
- **意图集合**：`咨询` / `办事`（采集 + 提交）/ `材料` / `进度` / 兜底闲聊。

### 2.3 对话与表单是同一份数据

| 动作 | 结果 |
| --- | --- |
| 用户在对话里说字段 | 自动回填到表单 |
| 用户在表单里改 | 回写对话上下文，并作为提交依据 |
| 提交 | **以表单为准**；自然语言只用于意图识别与字段抽取，不再作为"申请内容"展示 |

### 2.4 提交前必须校验（现在的 bug）

现在**不填任何信息也能点「开始办理」**，必须修：

1. **前端**：按 `collect_fields[].required` 校验；缺项时按钮置灰，并在字段下红字提示"必填"。
2. **默认值**：不要用 `0` / 空串冒充"已填"。数字型留空、开关型要求用户显式选择（或给出合理默认并在界面标注"默认值"）。
3. **后端兜底**：`/apply` 收到缺失必填项时返回 **400 + 缺失字段列表**，不进入编排。
4. **确认一步**：提交前把表单内容用**自然语言回述**给用户（"您要办的是：店名 XX，面积 80㎡，需装招牌——确认提交？"），用户确认后再提交。

## 3. 回复文案规范（不要甩 JSON）

### 3.1 现在的问题（都是反面例子）

```
信息采集Agent：已生成一次申请表单：{'name': '老张牛肉面', 'business_type': '热食/有油烟', ...}
条件判定Agent：需办理事项：['A_license', 'B_food_permit', 'E_health_cert']；材料：['身份证', ...]
材料核验Agent：核验结果：{'status': '通过', 'checked': 4, 'missing': [], 'model': 'qwen-vl'}
```

问题：Python 的 dict/list 字面量、内部事项 id（`A_license`）、字段 key、模型名（`qwen-vl`），**都不该给办事群众看**。

### 3.2 规范

1. **面向群众一律自然语言**：不出现 `{}`、`[]`、下划线 id、模型名、字段 key。
2. **术语换人话**：`A_license` → "营业执照"；`已受理 / 办理中 / 已办结` 本身已是人话，保留。
3. **结构走事件、文案走 message**：
   - 结构化数据（`flow_node` / `item_done` / `case_created`）→ 给界面渲染
   - 自然语言文案 → `message` 事件，进对话气泡
   两者**不要混在一条里**。
4. **每条文案 = 结论 + 依据 + 下一步**：

| 场景 | 现在的写法 | 应该写成 |
| --- | --- | --- |
| 采集 | `已生成一次申请表单：{'name': ...}` | 已记录：店名「老张牛肉面」、面积 80㎡。还差一项——是否设置户外招牌？ |
| 判定 | `需办理事项：['A_license', ...]` | 根据您的情况，需要办 4 件事：营业执照、食品经营许可证、健康证，外加户外招牌审批（因为您要装招牌）。 |
| 核验 | `核验结果：{'status': '通过', ...}` | 3 份材料都合格。还缺「经营场所证明」，需要您补一份。 |
| 提交 | `已生成办理单 YJS0006，并联提交至各部门` | 已受理，办理单号 YJS0006，已同时转给市场监管、卫健、城管，预计 5 个工作日。 |
| 办结 | `市场监管：个体工商户设立登记 -> 已办结` | 市场监管那边办好了，营业执照已出件。 |

5. **技术细节进日志**：模型名、耗时、内部 id 只写调试日志，不推进对话。
6. **不确定就问、失败就说**：模型超时/降级要如实告知，不要用"已通过"糊弄。

### 3.3 落地位置

- `app/orchestrator/main_agent.py`：`_log(...)` 推送的文本
- `app/agents/progress_agent.py`：进度看板文本
- `app/agents/consult_agent.py`：咨询回复
- 建议：各 Agent 增加**面向用户的文案**（`human_text`），内部数据继续走事件 payload
