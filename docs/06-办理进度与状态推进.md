# 06 办理进度与状态推进

## 为什么要有“进度”

本 Agent 代替群众走完整套办理流程，因此“办理进度”不是外部系统的黑盒，
而是这套流程自身的节点完成情况：**每完成一个环节就“打勾”**，
群众随时能查到“办到哪一步了”。

## 流程节点（主线，事件驱动）

由编排框架统一定义（`app/orchestrator/flow.py`），两个业务场景共用：

| 顺序 | 节点 | 由谁完成 | 打勾条件 |
| --- | --- | --- | --- |
| 1 | 意图识别 | 意图路由 | 识别出咨询 / 办事 / 查询意图 |
| 2 | 事项咨询 | 咨询 Agent | 返回办事要点 |
| 3 | 信息采集 | 信息采集 Agent | 生成结构化申请表单 |
| 4 | 条件判定 | 条件判定 Agent | 判定出事项与材料清单 |
| 5 | 材料核验 | 材料核验 Agent | 产出核验报告 |
| 6 | 并联提交 | 主 Agent | 生成办理单并提交各部门 |
| 7 | 各部门事项（动态） | 各部门事项办理子 Agent | 子 Agent 办结并回调主 Agent |
| 8 | 进度跟踪 | 进度跟踪 Agent | 生成进度看板并落库 |

节点状态流转：`待办 → 进行中 → 已完成`。
`MainAgent` 在每阶段开始调用 `flow.start()`、结束时调用 `flow.complete()`，完成即打勾；
当前进度会追加到编排轨迹（`trace`）中逐步展示。

> 第 7 项为**动态节点**：并联提交后，按场景事项清单为每个部门事项加入一个节点
> （key 即事项 id，如 `A_license`），插入在“并联提交”与“进度跟踪”之间。

## 各部门事项：子 Agent 办结后回调主 Agent

事项**不是靠时间或查询推进**，而是由办理该事项的部门子 Agent 上报结果驱动：

```
主 Agent --派发事项--> 部门子 Agent --办结回调 on_done(result)--> 主 Agent
                                                              ├─ 更新事项状态（gov.finish）
                                                              └─ 打勾对应流程节点（flow.complete）
```

- 子 Agent：`app/agents/item_agent.py` 的 `ItemAgent`，桩实现直接返回“已办结”；
  真实接入时替换为调用各部门政务系统接口 / 工具，**回调机制与主 Agent 无需改动**。
- 事项状态：`已受理 → 办理中 → 已办结`（`MockGovServices.STAGES`）：
  提交即“已受理”，`gov.start()` 置“办理中”，子 Agent 回调后 `gov.finish()` 置“已办结”。
- 回调逻辑：`MainAgent._on_item_done()`。

## 数据落地

`CaseRecord.flow` 保存流程节点台账快照，`item_status` 保存并联事项状态，
通过 `JsonFileRepo`（`data/runtime/cases.json`）落盘，支持跨进程按单号查询。
后续替换为数据库时，只需实现 `save_case / get_case / list_cases`。

## 接口与用法

```python
agent.run(utterance, answers)   # 走完整流程；部门子 Agent 办结后自动回调打勾
agent.query(case_id)            # 只读查询进度看板
```

```bash
python run_demo.py                 # 跑完流程（含各部门事项逐个打勾）
python run_demo.py --query YJS0001 # 按单号查询进度看板
```

## 后续扩展

- **App 进度看板**：uni-app 前端订阅事件流即时刷新（见 `docs/07`）。
- **真实部门对接**：把 `ItemAgent.process` 换成调用各部门政务系统接口，回调不变。
- **并发 / 异步办理**：部门子 Agent 目前串行调用；可改为并发，回调汇总后再出件。
