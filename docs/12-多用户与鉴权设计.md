# 12 多用户与鉴权设计

> 状态：**已实现（后端）**。对应 `docs/10-App打包前检查清单` 的第 4、5 条：
> 「服务端是单进程 + 内存状态」与「材料文件接口没有鉴权」。
> 前端（uni-app）登录界面尚未接入——默认 `AUTH_REQUIRED` 关闭，前端行为保持不变。

## 1. 要解决什么

上线前的两条硬门槛（`docs/10`）：

| # | 问题 | 后果 | 本文对应 |
| --- | --- | --- | --- |
| 4 | 会话 / 材料收集单 / 办理单 / 单号都在进程内存里 | `uvicorn --workers 4` 时会话互相找不到、并发提交重号 | 第 6 节：存储抽象 |
| 5 | 材料文件接口没有鉴权 | 谁知道 URL 谁就能下载身份证照片 | 第 4、5 节：鉴权 |

多用户还带来第三个问题：**数据归属**。同一套接口被多个办事人使用时，
必须保证 A 看不到 B 的会话、材料和办理单。这是安全层 RBAC（`docs/02`）的落点。

三条一起做，主线只有一句话：**给每条数据记上归属，给每个请求定下身份，按归属放行。**

## 2. 多用户主线：`owner_id` 贯通

三张核心数据都加了 `owner_id`（`app/models/schema.py`）：

| 模型 | 归属字段 | 何时写入 |
| --- | --- | --- |
| `CaseRecord` 办理单 | `owner_id` | `/apply` 跑编排时由请求用户带入（`MainAgent.run(..., owner_id=...)`） |
| `MaterialIntake` 材料收集单 | `owner_id` | 建收集单时写入（`MaterialService.plan(..., owner_id=...)`） |
| `SessionRecord` 多轮会话 | `user_id` | 建会话时写入（`AgentService.create_session(..., user_id=...)`） |

链路是**自上而下传递**的：

```
登录令牌 -> 当前用户 user_id
   -> create_session(user_id)              会话归属
   -> session.user_id -> intake.owner_id   收集单归属
   -> /apply(intake)  -> case.owner_id      办理单归属
```

`owner_id` 为空串表示**历史 / 演示数据**，不设限（向后兼容，见第 3 节）。

## 3. RBAC：谁能访问谁的数据

角色与权限定义在 `app/auth/models.py`：

| 角色 | 权限 | 说明 |
| --- | --- | --- |
| `applicant` 办事人 | `session:own` `material:own` `case:own` | 只能操作自己名下的数据 |
| `staff` 政务工作人员 | 上述 + **`case:any`** | 可跨用户查询**已受理的办理单**；读不到别人的会话草稿与材料 |
| `admin` 管理员 | `*` | 全部权限 |

判定只有一个入口——`User.can_access(owner_id, permission)`：

1. `owner_id` 为空 → 放行（历史 / 演示数据）；
2. `owner_id == 自己` → 放行；
3. 否则看是否持有对应跨用户权限（如 `case:any`）。

服务层用 `server/auth.py::ensure_access(user, owner_id, permission=...)` 落到 HTTP：
不通过即 **403**。各接口使用的权限：

| 接口 | 归属权限 |
| --- | --- |
| `/api/session`、`/api/chat`、`/api/fields`、`/api/sessions/{id}` | `session:own` / `session:any` |
| `/api/cases/{case_id}` | `case:own` / `case:any` |
| `/api/materials/...`（清单 / 上传 / 撤回） | `material:own` / `material:any` |
| `GET .../files/{file_id}` 读文件 | 归属人，或**绑定该文件的签名链接**（见第 5 节） |

> 会话用 `session:any` 而非 `case:any`：会话里是**尚未受理的草稿信息**，
> 工作人员只该看已受理的办理单。不然 `staff` 会顺带读到别人的草稿，越权。

## 4. 鉴权：口令、令牌、兼容开关

实现全在 `app/auth/`，**零第三方依赖**（只用标准库 `hashlib` / `hmac` / `secrets` / `base64`）：

- **口令**（`security.py`）：`hash_password` 用 PBKDF2-HMAC-SHA256（随机盐 + 迭代）
  存成 `pbkdf2_sha256$轮数$盐$散列`；校验用 `hmac.compare_digest` 防时序侧信道。
  **永不落明文、永不回显**。
- **令牌**（`security.py`）：自包含 `payload.signature`（两段 base64url），
  签名 HMAC-SHA256，claims 带 `sub` / `typ` / `exp`。服务端**无需存储**即可校验
  ——天然适配"会话进 Redis、服务多进程"的部署。
- **两类令牌**靠 `typ` 区分：
  - `typ="session"`：登录令牌，代表"我是某个用户"；
  - `typ="file"`：材料文件专用签名链接，**绑定到具体文件**（见第 5 节）。

`AuthService`（`service.py`）是账号与令牌的统一入口：
`register` / `login` / `issue_token` / `resolve` / `issue_file_token` / `verify_file_token`。

### 兼容开关 `AUTH_REQUIRED`

| 取值 | 行为 |
| --- | --- |
| 未设置（默认） | 未携带令牌的请求按**演示用户** `u_demo` 处理，单用户 Demo 与既有端到端流程行为不变 |
| `=1` | 强制登录，未登录返回 **401** |

关键细节：**带了令牌但令牌无效（过期 / 篡改）时不降级为演示用户**，直接 401。
否则"令牌过期"会静默变成"以演示用户身份通过"，是权限漏洞。

> 上线清单：把 `AUTH_REQUIRED=1`、显式配置 `AUTH_SECRET`（生产各实例一致），并接 HTTPS。

## 5. 材料文件鉴权

痛点在 `GET /api/materials/{intake_id}/{material_id}/files/{file_id}`：材料是敏感个人信息。

难点：**图片要能直接作为 `<image src>` 加载**，浏览器发 `src` 请求带不了自定义请求头，
所以令牌不能只放 `Authorization`。解法是给每张图签一个**绑定到该文件的短时链接**
（`AuthService.issue_file_token`），由 `MaterialService` 自动拼进 URL：

```
/api/materials/CL0001/id_card/files/a1b2c3?token=<base64url payload>.<签名>
```

claims 里的 `i` / `m` / `f` 分别是收集单号 / 材料 id / 文件 id，缺一不可对上；
有效期默认 10 分钟（`AUTH_FILE_URL_TTL`）——只够前端把图加载出来，不能扩散。

`read_file` 的两条合法路径：

1. **URL 带签名链接**且签名与 `(intake_id, material_id, file_id)` 完全匹配 → 放行；
2. 否则取请求头里的**登录令牌**，按归属校验（本人或 `material:any`）→ 放行。

都不满足：**401**（无凭证）/ **403**（凭证有效但非本人）。后续缩略图 / 预览都由
`MaterialView` 的 `url` 字段下发，前端无需自己拼。

## 6. 存储抽象与"留出的数据库接口"

`app/storage/base.py` 用**纯接口**把"状态存哪"和"业务怎么用"解耦，上层只依赖接口：

| 接口 | 现状 | 生产形态 | 关键方法 |
| --- | --- | --- | --- |
| `CaseRepo` 办理单 | `InMemoryRepo` / `JsonFileRepo` | PostgreSQL / MySQL | `save_case` / `get_case` / `list_cases(owner_id)` |
| `SessionRepo` 多轮会话 | `InMemorySessionRepo` | Redis（短期） | `put` / `get` / `drop` / `list_ids` |
| `UserStore` 用户账号 | `InMemoryUserStore` / `JsonFileUserStore` | PostgreSQL / MySQL | `add` / `get` / `find_by_username` / `password_hash_of` / `list_users` |
| `IdAllocator` 单号 | `InMemoryIdAllocator` / `JsonFileIdAllocator` | 数据库序列 / 分布式发号器 | `next` / `reserve` / `peek` |

`app/storage/factory.py::build_storage()` 是**唯一切换点**（环境变量 `STORAGE_BACKEND`）：

```
STORAGE_BACKEND=memory   全部进程内（测试用）
STORAGE_BACKEND=json     会话在内存、办理单 / 用户 / 单号落 JSON（默认，单机 Demo）
STORAGE_BACKEND=sql      预留：注入实现后启用
STORAGE_BACKEND=redis    预留：注入实现后启用
```

`sql` / `redis` **只留接口不接实现**：直接 `build_storage("sql")` 会抛出带说明的
`NotImplementedError`，列出还缺哪几个组件。真实接入时把实现注入即可，业务代码零改动：

```python
storage = build_storage(
    "sql",
    cases=SqlCaseRepo(dsn), sessions=SqlSessionRepo(redis), users=SqlUserStore(dsn),
    ids=SqlIdAllocator(dsn), materials=ObjectStorageMaterialStore(...),
)
app = create_app(storage=storage)
```

### 迁移步骤（以 PostgreSQL 为例）

1. **建表**（参考 `app/storage/base.py` 里的 DDL）：
   - `cases(case_id PK, owner_id, scenario_id, payload JSONB, created_at, updated_at)` +
     `INDEX(owner_id)`；`payload` 存 `CaseRecord.to_dict()`；
   - `users(user_id PK, username UNIQUE, password_hash, display_name, role, created_at)`；
2. 实现 `CaseRepo` / `UserStore` 的对应方法（`list_cases(owner_id)` ↔ `WHERE owner_id=:x`）；
3. 会话实现 `SessionRepo`：key `session:{id}` → `SessionRecord` 可持久化字段，读回时重建 Agent；
4. 单号换成数据库序列：`IdAllocator.next` ↔ `nextval('case_seq')`（或带 `INSTANCE_ID` 的发号器）；
5. 材料文件换对象存储：实现 `MaterialStore.add_file` / `path_of` 的等价能力（返回带签名的对象 URL）；
6. `STORAGE_BACKEND=sql` + 注入，跑 `tests/test_auth.py` 与 `tests/test_api_e2e.py` 回归。

> `INSTANCE_ID` 环境变量：多实例部署时给单号加实例号（`YJS0001` → `YJSi0001`），
> 跨实例也不会撞号；`IdAllocator.format` 统一处理。

## 7. 接口契约（新增）

| 接口 | 方法 | 用途 |
| --- | --- | --- |
| `/api/auth/register` | POST | 注册账号；接口**不接受自定义角色**（防提权），重名 / 弱口令 400 |
| `/api/auth/login` | POST | 账号口令登录，返回自包含令牌；凭据错误 401（不区分"用户不存在 / 密码错"，防枚举） |
| `/api/auth/me` | GET | 取当前用户（未开启强制鉴权时为演示用户） |
| `/health` | GET | 新增 `storage` / `auth_required`，一眼确认跑的是不是多用户形态 |

登录后客户端把 `token` 放进 `Authorization: Bearer <token>`（也兼容 `X-Auth-Token`）。
响应模型见 `server/schemas.py`（`UserOut` / `TokenOut`），并纳入
`tests/test_openapi_contract.py` 的"每个 JSON 路由都要有响应模型"校验。

## 8. 环境变量

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `AUTH_REQUIRED` | 关闭 | 置 `1` 强制登录；上线必须开启 |
| `AUTH_SECRET` | 无 | 令牌签名密钥；**生产必须显式配置且各实例一致**。未配置时开发环境落到 `data/runtime/auth_secret.key`（已忽略，不入库） |
| `AUTH_TOKEN_TTL` | 7 天 | 登录令牌有效期（秒） |
| `AUTH_FILE_URL_TTL` | 10 分钟 | 材料文件签名链接有效期（秒） |
| `STORAGE_BACKEND` | `json` | `memory` / `json` / `sql` / `redis` |
| `INSTANCE_ID` | 空 | 多实例发号前缀 |

密钥与令牌**从不进入 `/health` 或任何对外输出**（与 MoMA 密钥同样的安全约定）。

## 9. 测试与验算

```bash
python tests/test_auth.py    # 多用户与鉴权：口令 / 令牌 / 用户隔离 / 材料越权 / 文件签名链接 / 兼容开关
```

`tests/test_auth.py` 覆盖：

- **基元**：口令哈希每次不同且可校验、非法哈希不抛异常；令牌签名 / 篡改 / 过期 / 换密钥失效；
- **服务**：注册（重名、弱口令）、登录（错口令、不存在用户）、令牌解析；文件签名链接绑定到文件；
- **HTTP 隔离**（`AUTH_REQUIRED=1`，内存存储）：未登录 401；A 的会话 / 材料 / 办理单 B 全部 403；
  `staff` 可跨用户查办理单但读不到会话与材料；文件"带签名可读、无凭证 401、篡改 401、别人令牌 403"；
- **兼容**：`AUTH_REQUIRED` 关闭时未登录 = 演示用户，单用户流程不变；
  但**携带无效令牌仍 401**（不静默降级）。

既有测试（`test_api_e2e` / `test_server_smoke` / `test_materials` / `test_flow` /
`test_openapi_contract`）在改造后**行为不变、全部通过**——因为它们默认走演示用户路径。

## 11. 与真实政务 / 上线的衔接

| 能力 | 现状 | 上线前 |
| --- | --- | --- |
| 传输 | HTTP（局域网明文） | HTTPS（并收紧 `network_security_config`，见 `docs/10` 第 6 条） |
| 令牌吊销 | 自包含、无状态，不支持主动登出 | 把已签发令牌的 `jti` 记入黑名单（Redis）即可 |
| 注册 | 用户名 + 口令，任意注册 | 实名 / 短信验证码 / 邀请码；角色只能由后台授予 |
| 审计 | 未落审计日志 | 登录、材料读写、受理等关键操作记审计（谁、何时、对哪条数据） |
| 脱敏 | 材料仅落本地磁盘 | 加密传输与存储、访问控制、脱敏留存（`docs/09` 第 9 节） |
| 数据层 | JSON / 内存 | Redis（会话）+ PostgreSQL/MySQL（办理单 / 用户）+ 对象存储（材料） |
