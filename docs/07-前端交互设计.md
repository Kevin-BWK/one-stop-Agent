# 07 前端交互设计（uni-app：Vue 3 + TypeScript，事件推送）

> 前端形态为 **uni-app（Vue 3 + TypeScript）**：**最终成品为 App**，H5 仅用于开发调试。
> **前端尚未实现**；其依赖的编排事件出口（第 6 节）已就绪。

## 1. 形态与技术选型

| 方案 | 结论 |
| --- | --- |
| **uni-app（Vue 3 + TypeScript）** | **采用**：App 为最终成品，H5 仅用于调试 |

前端技术栈：**uni-app（Vue 3 Composition API）+ TypeScript + Pinia**；
UI 组件库待选（uni-ui / uView / Element Plus 等）。多端差异见第 9 节。

## 2. 用事件推送

进度看板反映**真实办理进度**：

- 采用**服务端推送**：后端每完成一个流程节点 / 每收到一次部门子 Agent 回调，
  就**立即把事件推给前端**，类似中断通知；前端被动接收并增量更新界面。

| 方案 | 结论 |
| --- | --- |
| SSE（Server-Sent Events） | H5 端浏览器原生支持 → **H5（调试端）采用** |
| **WebSocket（`uni.connectSocket`）** | App 端不支持 `EventSource`，长连接只有它稳 → **App（成品端）采用** |

单个办件全程事件量约 20～30 条，长连接完全够用。**两端事件负载格式完全一致**
（都是 `Event.to_dict()` 的 JSON），只是传输载体不同：App 走 WebSocket，H5 走 SSE。

## 3. 交互时序

```
前端 uni-app（App 成品 / H5 测试）        后端 FastAPI + 编排层
        |  POST /apply  ------------------->  主 Agent 启动编排
        |  <-- event: message          （咨询应答 / 表单生成 / 核验报告…）
        |  <-- event: flow_node        （信息采集节点完成，打勾）
        |  <-- event: flow_node        （条件判定节点完成，打勾）
        |  <-- event: case_created     （办理单已生成，拿到单号）
        |  <-- event: flow_node        （并联提交完成）
        |  <-- event: item_done        （市场监管：个体工商户设立登记 已办结）
        |  <-- event: item_done        （卫健：从业人员健康证 已办结）
        |  ...
        |  <-- event: finished         （全流程结束，附最终 flow / item_status）
        |  流结束，连接关闭
```

- 事件**在发生的那一刻**推送，前端所见即真实进度，无需动画、无需轮询。
- 前端只维持**一条长连接**；仅在"回看历史单号"或"断线兜底"时调一次 `GET /cases/{case_id}`。

## 4. 事件契约

事件负载是**同一份 JSON**（由 `Event.to_dict()` 序列化），两端只是装帧方式不同：

**H5（SSE 帧）：**

```
id: 7
event: flow_node
data: {"type":"flow_node","data":{"key":"collect","name":"信息采集","status":"已完成","detail":"已生成一次申请表单","updated_at":"2026-09-21 10:00:00","done":3,"total":11}}
```

**App（WebSocket 消息体）：**

```
{"type":"flow_node","data":{"key":"collect","name":"信息采集","status":"已完成","detail":"已生成一次申请表单","updated_at":"2026-09-21 10:00:00","done":3,"total":11}}
```

- `id`：自增整数，用于断线重连（`Last-Event-ID`）。
- `event`：事件类型，见下表（WebSocket 端即 JSON 里的 `type`）。
- `data`：事件负载，字段复用现有数据结构，不另造模型。

| 事件类型 | 触发时机 | `data` 关键字段 |
| --- | --- | --- |
| `message` | Agent 产出对话文本（咨询应答、表单生成、核验报告等） | `stage`, `text` |
| `flow_node` | 流程节点状态变化（打勾），对应 `flow` 节点快照 | `key`, `name`, `status`, `detail`, `updated_at`, `done`, `total` |
| `case_created` | 并联提交生成办理单 | `case_id`, `scenario_id`, `items`, `materials` |
| `item_done` | 部门子 Agent 办结某事项 | `item_id`, `name`, `department`, `output`, `status` |
| `finished` | 全流程结束 | `case_id`, `flow`, `item_status` |
| `error` | 编排异常 | `code`, `message` |

字段与现有代码的对应关系：

| 事件字段 | 来源 |
| --- | --- |
| `flow_node.*` | `FlowProgress.snapshot()`（`app/orchestrator/flow.py`） |
| `item_done.*` | 部门子 Agent 回调结果（`app/agents/item_agent.py`） |
| `case_created.*` / `finished.*` | `CaseRecord`（`app/models/schema.py`） |
| `message.text` | `MainAgent.run` 的 `trace` 条目文本 |

## 5. 接口契约

| 接口 | 方法 | 用途 | 返回 |
| --- | --- | --- | --- |
| `/apply` | GET / POST | 提交申请并开始办理（H5 调试端）。`EventSource` 只能发 GET，故查询参数形式为 `?scenario_id=&utterance=&answers=<json>`；POST JSON 亦支持 | SSE 事件流（第 4 节全部事件） |
| `/ws/apply` | WebSocket | 提交申请并开始办理（App 成品端，`uni.connectSocket`） | 同样的 JSON 事件 |
| `/cases/{case_id}` | GET | 按单号查询进度看板（回看 / 断线兜底） | `CaseRecord` JSON（含 `flow` / `item_status`） |
| `/scenarios/{scenario_id}` | GET | 取场景字段定义，前端动态渲染表单 | `collect_fields`、`items`、`condition_rules` |

`/apply` 请求体（沿用现有信息采集字段）：

```json
{
  "scenario_id": "restaurant_open",
  "utterance": "我想在学校旁边开一家牛肉面馆",
  "answers": {"name": "老张牛肉面", "business_type": "热食/有油烟", "area_sqm": 80, "signboard": true}
}
```

H5 端 SSE 响应头：

```
Content-Type: text/event-stream
Cache-Control: no-cache
Connection: keep-alive
```

## 6. 与现有代码的衔接（事件出口已就绪）

`MainAgent.run(utterance, answers, on_event=None)` 与 `query(case_id, on_event=None)`
已支持可选事件回调，**不传时行为与以往完全一致**（`run_demo.py` 与冒烟测试不受影响）。

- 事件对象：`app/orchestrator/events.py` 的 `Event(type, data)`，`Event.to_dict()` 可直接 JSON 序列化；
  类型常量 `MESSAGE / FLOW_NODE / CASE_CREATED / ITEM_DONE / FINISHED / ERROR`。
- `message` 只推送**面向用户的文本**（咨询应答、采集表单、核验结果、部门办结、进度看板）；
  内部轨迹（意图路由、进度条）不推送，避免污染聊天区。
- 节点打勾 → `flow_node`；并联提交 → `case_created`；部门办结 → `item_done`；结束 → `finished`。
- 编排异常先推 `error` 再抛出，前端可据此提示并恢复界面。
- 服务层（FastAPI）只需把 `Event.to_dict()` 写进 SSE 流 / WebSocket 帧，编排层无需再改。

## 7. 前端工程结构（规划）

```
frontend/                       # uni-app 工程（Vue 3 + TypeScript）
├── pages.json                  # 页面与导航配置
├── manifest.json               # App（成品）/ H5（调试）构建配置
├── tsconfig.json
├── vite.config.ts
└── src/
    ├── main.ts
    ├── App.vue
    ├── api/
    │   ├── http.ts          # GET /cases、GET /scenarios
    │   └── stream.ts        # 事件流订阅（App 用 uni.connectSocket；H5 用 EventSource）
    ├── types/contract.ts    # 与后端事件 / 办理单一致的 TS 类型
    ├── stores/case.ts       # Pinia：单号、节点集合、事项状态
    └── components/
        ├── ChatPanel.vue      # 聊天区
        ├── DynamicForm.vue    # 由 collect_fields 动态渲染
        └── ProgressBoard.vue  # 按 key 增量更新
```

`types/contract.ts` 的职责是**把后端契约翻译成 TS 类型**（`FlowNode` / `ItemEvent` / `CaseCreatedEvent` /
`MessageEvent` / `FinishedEvent` / 判别联合 `OrchestratorEvent`），保证前后端字段一致。

表单区**不硬编码字段**，直接消费 `collect_fields`：`type` 决定控件
（`text` → 输入框、`enum` → 下拉、`number` → 数字框、`bool` → 开关），
`options` 填充选项、`required` 决定校验；新增"一件事"只需加场景配置，前端无需改动。

## 8. 界面行为与容错

界面行为：

- **提交**：聊天区输入开场白（或点选场景）后建立事件流连接（App: WebSocket；H5: SSE）；办理期间提交按钮置灰。
- **表单**：由场景字段渲染并做必填校验，采集结果即 `answers` 传给后端。
- **进度看板**：以 `key` 为索引维护节点集合，收到 `flow_node` 只更新对应节点，
  收到 `item_done` 更新并联事项，`done / total` 驱动进度条——不整体重绘。
- **回看**：凭办理单号调 `GET /cases/{case_id}` 渲染历史进度。

容错：

- **断线重连**：事件带自增 `id`；重连时前端携带 `Last-Event-ID`，后端从该 id 之后续推。
- **办理结果不丢**：连接中断不影响编排；办理单已落盘（`data/runtime/cases.json`），
  重新连上或调用 `GET /cases/{case_id}` 即可拿到最终进度。
- **心跳**：长连接期间定期发送 SSE 注释行（`: ping`），防止反向代理 / 网关因空闲断流。
- **兜底查询**：未收到 `finished` 时按单号补查一次最终状态，避免界面卡在中间态。
