# 07 前端交互设计（PySide6 桌面客户端）

> GUI 形态为 **PySide6（Qt for Python）桌面客户端**，不做微信小程序、不做 Web 门户。
> **GUI 尚未实现**；其依赖的编排事件出口（第 5 节）已就绪。

## 1. 形态与技术选型

| 方案 | 结论 |
| --- | --- |
| 微信小程序 | 需云端服务与备案，演示链路长 → 不用 |
| Web 门户（Vue / React） | 需额外起服务、前后端联调成本高 → 不用 |
| **PySide6 桌面客户端** | **采用**：与编排层同进程、即开即用、离线可跑、跨平台 |

桌面端与编排层**同进程**运行，因此：

- 不需要 HTTP 服务、不需要 SSE / WebSocket，也**不存在前端轮询**。
- 进度推送直接走 **Qt 信号 / 槽（Signal & Slot）**，比网络推送更直接、零延迟。

## 2. 界面结构（三区布局）

```
+---------------------------------------------------------------+
|  ChatPanel                     |  FormPanel                   |
|  聊天区：多轮对话                |  动态表单区：由场景字段自动渲染   |
|  · 用户开场白                    |  · text   -> QLineEdit        |
|  · 咨询应答 / 采集追问            |  · enum   -> QComboBox        |
|  · 核验结果 / 进度播报            |  · number -> QSpinBox         |
|                                |  · bool   -> QCheckBox        |
|--------------------------------+-------------------------------|
|  ProgressPanel  进度看板                                        |
|  · 流程节点清单（打勾）+ QProgressBar                          |
|  · 并联事项状态（部门 / 事项 / 状态）                            |
|  · 办理单号（可复制，用于回看）                                   |
+---------------------------------------------------------------+
```

表单区**不硬编码字段**，直接消费 `scenarios/*.json` 的 `collect_fields`
（`type` 决定控件类型、`options` 填充下拉、`required` 决定校验），
新增"一件事"只需加场景配置，GUI 无需改动。

## 3. 线程模型

编排过程可能耗时（未来接入 MoMA 真实 API / 网络请求），会阻塞界面；且 Qt 规定
**只能在主线程操作控件**。因此：

```
主线程（UI）                                后台 QThread
  MainWindow
   ├─ ChatPanel          <-- 信号 --+
   ├─ FormPanel                    |
   └─ ProgressPanel                |
         ▲                          |
         | Qt 信号（自动排队到主线程）  |
         |                          |
   OrchestratorWorker  -------------+
      调用 MainAgent.run(utterance, answers)
      通过 on_event 回调 -> emit 信号
```

编排放在 `QThread` 中执行，事件通过信号**自动排队回主线程**再刷新界面；
严禁在 worker 线程里直接操作控件。

## 4. 编排事件 → Qt 信号

沿用 `docs/06` 的办理进度语义，只是传输方式从网络推送换成 Qt 信号，**字段不变**：

| 事件 | Qt 信号 | 负载 | 界面响应 |
| --- | --- | --- | --- |
| `message` | `message_ready(stage, text)` | Agent 文本（咨询应答 / 核验报告 / 进度播报） | 聊天区追加气泡 |
| `flow_node` | `flow_node_changed(node, done, total)` | `flow` 节点快照（`key/name/status/detail`） | 看板更新该节点 + 进度条 |
| `case_created` | `case_created(case)` | `case_id` / `items` / `materials` | 显示办理单号与事项清单 |
| `item_done` | `item_done(item)` | 部门 / 事项 / 状态 / 出件 | 看板更新并联事项 |
| `finished` | `run_finished(case)` | 最终 `flow` / `item_status` | 结束态、解除按钮禁用 |
| `error` | `run_failed(message)` | 异常信息 | 弹窗提示 + 恢复可用 |

数据来源与 `docs/06` 完全一致：

| 信号字段 | 来源 |
| --- | --- |
| `flow_node` | `FlowProgress.snapshot()`（`app/orchestrator/flow.py`） |
| `item_done` | 部门子 Agent 回调结果（`app/agents/item_agent.py`） |
| `case_created` / `finished` | `CaseRecord`（`app/models/schema.py`） |
| `message` | `MainAgent.run` 的 `trace` 条目文本 |

## 5. 与现有代码的衔接（事件出口已就绪）

`MainAgent.run(utterance, answers, on_event=None)` 与 `query(case_id, on_event=None)`
已支持可选事件回调，**不传时行为与以往完全一致**（`run_demo.py` 与冒烟测试不受影响）。

- 事件对象：`app/orchestrator/events.py` 的 `Event(type, data)`；
  类型常量 `MESSAGE / FLOW_NODE / CASE_CREATED / ITEM_DONE / FINISHED / ERROR`。
- `message` 只推送**面向用户的文本**（咨询应答、采集表单、核验结果、部门办结、进度看板）；
  内部轨迹（意图路由、进度条）不推送，避免污染聊天区。
- 节点打勾 → `flow_node`；并联提交 → `case_created`；部门办结 → `item_done`；结束 → `finished`。
- 编排异常先推 `error` 再抛出，GUI 可据此提示并恢复界面。
- 桌面端 `OrchestratorWorker` 只需把 `Event` 转成 Qt `emit` 信号，编排层无需再改。

## 6. 界面行为

- **提交**：聊天区输入开场白（或点选场景）后触发编排；编排期间提交按钮置灰，避免重复提交。
- **表单**：由场景字段渲染并做必填校验；采集结果即 `answers` 传给编排层。
- **进度看板**：维护以 `key` 为索引的节点集合，收到 `flow_node` 增量更新对应节点，
  收到 `item_done` 更新并联事项，`done / total` 驱动进度条——不整体重绘。
- **回看**：凭办理单号调用 `MainAgent.query(case_id)` 渲染历史进度（数据已在
  `data/runtime/cases.json` 落盘）。

## 7. 容错

- 编排异常 → `error` 事件 → 弹窗提示，界面恢复可用。
- 结果不丢：办理单实时落盘，重开客户端可凭单号回看最终进度。
- 取消：当前编排为同步流程，先不支持中途中断，仅通过按钮置灰防止重复提交。
